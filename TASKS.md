## P1 — Secure end-to-end data channel (mandatory cloud-sync gate)

Owner scope clarification: protect all transmitted user data against network observers and cloud intermediaries. Local application history may remain plaintext under normal OS access controls; no application-level encryption of SQLite/IndexedDB, local files, indexes or caches is required. No legacy data migration, re-encryption or migration UI is required (there is no history to migrate). Keep cryptographic keys and authentication tokens in protected OS storage. Do not silently delete existing data or weaken unrelated safeguards.

- [ ] S1 — Common secure channel: define a small, versioned, interoperable E2EE transport layer shared by Android and Linux UI/background agents. MANDATORY v1 suite: libsodium XChaCha20-Poly1305-IETF (crypto_aead_xchacha20poly1305_ietf_*, 32-byte key, fresh 24-byte random nonce from randombytes_buf, 16-byte tag); libsodium crypto_kdf (BLAKE2b, 32-byte subkeys, fixed 8-byte contexts LUrecord and LUfilekw, subkey ID 1); Ed25519 detached signatures for device identity, signed records and trust-control messages; X25519-based libsodium crypto_box_seal for encrypted key distribution, with separate verified Ed25519 signature (sealed boxes alone do not authenticate the sender). Android: pinned stable libsodium via NDK/JNI or maintained binding exposing the exact APIs; Linux: PyNaCl plus a narrow libsodium binding if an API is unavailable. Use native crypto in the agents, not custom WebView JavaScript, and do not expose raw keys to the UI. Use OS CSPRNG, strict decoding and replay/deduplication checks. Specify a canonical, unambiguous binary header (version, account UUID, record UUID, sender device UUID, epoch, nonce; fixed widths, big-endian integers) as AEAD AAD, with Ed25519 domain-separated signature over header and ciphertext. Put sensitive type/time/name fields inside ciphertext. Unknown version, missing signature, wrong account or epoch and malformed input must fail closed. Do not invent cryptography. Use HTTPS/WSS with certificate validation in addition to E2EE; prefer TLS 1.3, minimum TLS 1.2 where platform/provider requires it. Centralize encryption/decryption so future sync modules use the same mandatory boundary rather than implementing independent protocols. Reject plaintext or invalid ciphertext; no downgrade/fallback. Document the threat model and exact v1 wire format in SECURITY_PROTOCOL.md before implementation; include shared test vectors and a security review of enrollment/rotation and parsing. Use existing primitives only, not a claim that the assembled application protocol has been externally audited.
- [ ] S2 — Trusted devices and keys: generate independent X25519 and Ed25519 key pairs for each device and a random 32-byte account data key for each epoch. Existing trusted device and new device must verify both sets of public keys out of band (QR or comparison of a transcript fingerprint of at least 128 bits, bound to account, both device identities, roles and expiring one-time enrollment challenge); require owner confirmation. The existing trusted owner device distributes the account epoch key using crypto_box_seal to the verified X25519 public key, then signs the complete recipient/account/epoch/challenge-bound envelope with Ed25519. Verify signature and trust chain before unsealing; verify proof of possession during enrollment. Never upload unwrapped private or data keys to the cloud. Use a single owner-authorized writer for signed membership/epoch changes in v1, persist highest accepted epoch and reject known stale rosters; do not claim protection against a malicious server withholding a new revocation from an offline device. Queue local records until current trust state can be checked; distribute fresh epoch keys only to remaining approved devices on revocation. Explicitly document that this is stored-history encryption, not a forward-secret Signal ratchet. Protect local keys and authentication credentials with Android Keystore and Linux Secret Service/keyring (or a secure explicit-unlock fallback). Keep normal local application data unchanged. Provide device removal/key rotation for future transfers and a clear recovery/re-pairing path; do not promise revocation of already obtained historical keys. Keep the setup simple for personal use.
- [ ] S3 — Route ALL synchronized user content through this common secure channel: Transfer text/links, clipboard, file bytes and names, Activity/application names, usage timestamps, unlock/screen events and GPS coordinates/accuracy, plus future synced user content. Encrypt on the sending device BEFORE network upload; decrypt only on trusted receiving devices. Supabase and Google Drive/Yandex Disk must receive/store only ciphertext for user payloads, with minimal required routing metadata (account/opaque IDs, operational timing and sizes as necessary). Keep RLS and OAuth access controls. Use the same versioned envelope for records. For files use libsodium crypto_secretstream_xchacha20poly1305 with a fresh random 32-byte per-file key, wrapped in the encrypted signed manifest using the LUfilekw subkey and a fresh random 24-byte nonce, binding file/account/epoch IDs. Use 1 MiB plaintext chunks (configurable in a future version only), length-prefixed frames, authenticated file ID and chunk index as associated data, 24-byte stream header, required TAG_FINAL, verified manifest length and no trailing data. Keep plaintext filename/MIME/size in encrypted manifest; use opaque cloud object IDs. For retries reuse identical staged ciphertext, or regenerate file key and header on full restart; never reuse an altered stream state/nonce. Verify complete stream before exposing download; bounded memory and preserve provider upload progress/resume where supported. Preserve async/offline delivery when the other device is switched off, background sync, local history/search and UI. Never upload keystrokes or microphone data.
- [ ] S4 — Fresh encrypted cloud format: update the schema and upload/download paths as needed for ciphertext; use a new versioned namespace/schema or equivalent cutover that rejects legacy plaintext writers. No migration of old records or local storage overhaul. Do not automatically delete any old data; report if unexpected legacy data exists. Protect the network boundary even when keys are unavailable, by keeping data locally queued or pausing cloud sync; do not fall back to plaintext. Ensure all providers, native background collectors, retry paths and Realtime use the protected route. Avoid leaking payloads/tokens/keys through logs or diagnostics. Keep existing signed-release and access-control safeguards.
- [ ] S5 — Acceptance: cross-platform known-answer tests and real Android <-> Linux encrypted round trips for each content type, including offline delivery, large/empty files, failed/retried uploads, process restart, wrong keys, tampering, replay, untrusted/revoked device, cross-account isolation and interrupted transfer. Inspect actual outgoing requests and raw Supabase/Drive data with synthetic canaries; demonstrate user content is ciphertext and cloud credentials alone cannot decrypt it. Verify local history still behaves normally. Document residual observable metadata and endpoint compromise limitations; record CI evidence and physical-device gaps in STATUS.md. Do not enable sensitive cloud sync before its applicable tests pass or claim formal audit completion. No automatic production publication.
