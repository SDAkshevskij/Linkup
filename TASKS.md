## P1 — Security foundation and encrypted data (mandatory release gate)

- [ ] S1: Write a threat model and data-flow inventory in SECURITY.md, covering WebView/Qt, Android/Linux collectors, Supabase REST/Realtime/RLS, cloud drives, storage, IPC, backups, logs, temporary files, OAuth and updates. Distinguish E2EE, local encryption, TLS, authentication and authorization; document malicious server/account, device enrollment, compromised endpoint, metadata and availability limits.
- [ ] S2: Select maintained, reviewed interoperable crypto libraries and a versioned authenticated envelope format. Use AEAD (AES-256-GCM with guaranteed nonce uniqueness or XChaCha20-Poly1305), OS CSPRNG, HKDF domain separation, authenticated account/record/type/key epoch context and strict parsing. No homemade crypto, hardcoded keys, unauthenticated encryption or plaintext fallback. Add cross-language known-answer tests Android/Linux; specify nonce, AAD, serialization and key lifecycle.
- [ ] S3: Separate Supabase login from cryptographic device trust. Generate independent device identities and data keys locally; use a reviewed authenticated key agreement/wrapping protocol (e.g. HPKE where appropriate), trusted device approval with authenticated QR/fingerprint, expiring single-use challenges and protection against server key substitution/replay. Provide trusted-device list, revocation and key rotation for future records; document previously obtained keys cannot be revoked retroactively. Provide optional user-controlled high-entropy recovery key or Argon2id-protected recovery bundle, never send raw keys/recovery secrets to cloud. Test loss, reinstalls, concurrent enrollment, offline/revoked devices and wrong recovery secret.
- [ ] S4: Protect local keys and credentials via Android Keystore and Linux Secret Service/keyring with secure explicit unlock fallback, not plaintext. Remove Supabase session from WebView LocalStorage and protect native background sessions as well. Encrypt sensitive local SQLite/IndexedDB/blob data, queues, indexes, caches, WAL/journals, backups and temporary files through vetted storage or authenticated record encryption. Restrict backups, permissions, logs and bridge APIs; never expose raw private keys to UI JS. Handle locked key stores by safely queuing or pausing; preserve local-only operation. Audit WebView/Qt origins, navigation, input escaping and IPC caller identity.
- [ ] S5: E2EE for Transfer text/links and Clipboard records, before upload and after receipt only on trusted devices. Encrypt content and sensitive filenames, MIME types/device labels and metadata where feasible; minimize and document residual routing/timing/size data. Supabase stores opaque ciphertext with RLS and authenticated IDs/key epochs, enforce schema limits for ciphertext overhead, deduplicate/reject replay and malformed data. Search and preview locally. Verify two independent devices can exchange data and cloud/account access alone cannot decrypt it.
- [ ] S6: E2EE for files on Google Drive/Yandex Disk, including filenames and sensitive metadata. Use reviewed streaming/chunked AEAD with authenticated manifest, ordering, length and final marker, fresh per-file keys/safe derivation and nonce-safe retries. Keep bounded memory, progress, resume/cancel/cleanup; do not expose partially verified downloads or plaintext cloud/temp files. Test zero-byte, boundary/large files, reordering, truncation, substitution, interrupted transfers, quota and disk-full cases.
- [ ] S7: E2EE for Activity, including Android/Linux background uploads, application names, usage/unlock/screen events and GPS coordinates/accuracy. Keep only necessary routing metadata in clear; preserve local aggregation, day filters and offline collection. Inspect actual raw database rows for absence of sensitive plaintext. Map links disclose location only on deliberate user action. Do not enable sensitive cloud Activity before this gate passes.
- [ ] S8: Transport and authorization hardening: HTTPS/WSS only for production, certificate validation, trusted redirect destinations, no bearer token leaks, least OAuth scopes, RLS on every cloud/device/account table and real cross-account denial tests. Harden Linux release verification with signed metadata/artifacts and a trusted public key (hash alone is not authenticity), preserve Android signing continuity, restrict CI permissions, pin/audit dependencies, scan secrets and vulnerabilities.
- [ ] S9: Safe versioned migration of existing plaintext local/cloud text, files, Activity and sessions. Explicit encrypted backup, resumable/idempotent conversion, verify decryption and data retention before owner-approved deletion; reject old plaintext writers after cutover, handle interruption, quota, concurrent devices and rollback without plaintext fallback. Explain provider backup/version retention and prior leakage; do not promise retroactive secrecy or guaranteed secure erasure. Prevent stale devices reuploading deleted records.
- [ ] S10: Security settings and release acceptance: encryption/key status, trusted devices, recovery, revoke, migration progress, lock/unlock and useful errors. Test actual Android/Linux exchange, encrypted offline queue, process death, restart, permission denial, wrong keys, malformed ciphertext, tampering, replay, revoked devices, upgrade and recovery; inspect Supabase/Drive/local storage/logs/network with synthetic canaries, verify no sensitive plaintext leaks. Include CI evidence, independent review where feasible, explicit physical-device gaps and residual risk in STATUS.md. Do not claim a formal audit or ship sensitive cloud features until their applicable security gates pass. No automatic production publication.
