# LinkUp — instructions for coding agents

Read PROJECT_CONTEXT.md, PRODUCT_QUALITY.md, EXECUTOR_PLAYBOOK.md, ARCHITECTURE.md, ROADMAP.md, TASKS.md, STATUS.md and CHANGELOG.md before changing code. Inspect the current branch and latest GitHub Actions results; documentation is a handoff, not proof of current behavior. User requests take priority over proposed roadmap items. TASKS.md is the authoritative priority/dependency and acceptance contract; ROADMAP.md is a summary, not a second backlog. Follow the newest owner decisions in the reviewed planning branch if they are not yet merged into main. Never treat a documentation-only planning PR as implementation evidence.

- Current project directory: `linkup-v0.2.0/`. Active CI: root `.github/workflows/android.yml`. Nested workflow is an archival duplicate; do not use it as the active workflow.
- Preserve Android and Linux Mint support and existing Transfer and Activity functionality. Do not silently replace native agents with a web-only app.
- Preserve colored daily activity timelines and responsive behavior per platform.
- **Product/design rule:** do not ship developer/admin-looking UI. “Simple” must not mean raw forms, a vertical stack of labels and buttons, default browser/Qt scrollbars, default-looking selects/checkboxes, or one permission button beside every field. Every user-facing surface must look intentionally designed and consistent with LinkUp's dark, bold visual identity. Prefer strong hierarchy, integrated controls, custom states, compact progressive disclosure, visual feedback, motion where useful, and platform-aware touch interactions. Use one primary action per surface where possible. Hide advanced/diagnostic controls behind a deliberate secondary surface (icon, sheet, inspector), without making important state invisible.
- Permission UX must be integrated into the feature control: a user-initiated toggle/card may launch the required Android settings/runtime permission flow, then reflect granted/denied state automatically on resume. Do not add a separate “grant permission” button for each capability unless the OS technically requires an explicit external action that cannot be represented naturally. Keep permissions transparent and reversible.
- Never expose unstyled native/browser scrollbars in the main product UI. Use touch/gesture scrolling and a subtle themed overlay/fading indicator only when a visible scroll affordance is useful. Preserve accessibility, keyboard use and large-enough touch targets; visual ambition is not a reason to reduce usability.
- Tracking must be opt-in on owned devices, respect OS permissions and revocation. No hidden monitoring, arbitrary remote shell, or insecure bypasses. Keep real activity data, credentials, OAuth tokens, signing keys and personal information out of this public repository and CI artifacts. Test with synthetic data.
- PRODUCT_QUALITY.md and EXECUTOR_PLAYBOOK.md are binding acceptance/operational contracts. Do not treat design as polish after functionality, and do not treat the currently listed tests as the complete test plan. Before implementation, derive additional edge cases from the changed state machine, OS APIs, persistence and failure modes. A feature can be rejected for generic design or insufficient adversarial coverage even when it technically works.
- Prefer small, reviewable commits or PRs; never force-push or overwrite concurrent work. Check git status and latest main before starting.
- Run relevant tests (commands in ARCHITECTURE.md), build and lint Android changes, and use emulator tests when available. Fix root causes rather than disabling checks. Never claim tests passed without evidence. Distinguish compiled APK from emulator-tested APK and real-device validation.
- After each substantial task update TASKS.md, STATUS.md and CHANGELOG.md with actual changes, remaining blockers, exact test commands/results, and CI run links. Update architecture/context only when decisions change. If a new user request conflicts with backlog, record the new decision.
- For handoff between ChatGPT and Codex, write the next actionable step and commit/branch in STATUS.md. Push a branch / open PR as appropriate; changes are shared only after they reach GitHub. Do not publish secrets or unreviewed private conversation text.

- Security scope: enforce the fixed LinkUp Security v1 suite and common end-to-end boundary in TASKS.md (S1–S5); document exact wire formats in SECURITY_PROTOCOL.md before implementation. No local-history encryption or legacy migration. Cloud user content must never fall back to plaintext. Keep private keys and auth tokens in protected OS storage. Do not send private source archives, personal data or production credentials to public GitHub or CI.
- Work on the highest-priority unblocked task; isolate changes into reviewable PRs. P0 safety containment and Activity repair do not require completing the P2 redesign. Owner-only credentials, real-device checks and release approval are explicit blockers for those steps, not for unrelated implementation.
